# Human Intervention Management

Own intervention timing and continuity of two independent authorization states. Read [approval layers](references/approval-layers.md) when permissions or pending decisions are involved. Domain workflows determine content; service workflows inspect and apply operations.

Resolve named companions from available skills or their source; sibling links locate them in this repository, not in every single-skill installation. If unavailable, report the capability gap and continue independent work; do not install or activate them implicitly.

## 1. Recover authority and access separately

Bind task authorization to the actual action, target, and phase, retaining exclusions, holds, and reserved decisions. Recover it from the existing conversation/task state across sessions. Re-evaluate harness access in the current environment under its actual scope and lifetime. Neither layer establishes the other; a pending publication decision does not make authorized preparation unapproved.

Reuse the operation plan to identify immediate effects, dependencies, readiness, applicable authority, valid grants, and known/likely/unknown interaction boundaries. Use documented controls and observed behavior; do not trigger avoidable effects to test a forecast. Describe permission requests by truthful immediate effects and the applicable instruction. Split calls that combine authorized and undecided effects, or resolve the genuinely missing authority first.

## 2. Continue work or arrange attention

Execute authorized, accessible operations autonomously, including effectful operations within scope. A fresh exchange or attendance window is needed only when human attention is needed or plausibly expected, not for every write or unknown boundary. Uncertainty alone does not justify waiting: inspect available documentation/state and proceed under current tool rules when no concrete interaction dependency prevents it. If a prompt occurs, follow the actual harness flow.

For operations expected to require attention:

1. Finish available investigation, staging, validation, and the concrete version needed for any reserved task decision. If initial access is indispensable, group that setup first, then return to autonomous preparation.
2. Reuse a fresh relevant exchange or agreed availability window, announce the bounded work, and start promptly. If availability is genuinely missing, establish timing once for the expected interaction; do not ask for the same task decision again or repeatedly check presence.
3. Execute prepared operations in dependency order, using supported batching, narrow access, and essential target/readback checks. Keep redesign, lengthy research, cosmetic work, and extended reporting outside the attended period. Never trade scope or verification for speed.
4. If a new dependency requires substantial preparation, stop safely and release the user. Close the attended period explicitly, identifying remaining potentially interactive work; regroup rather than scatter later requests.

Honor required task decisions independently of this scheduling. Success means less fragmented human attention, not a promised dialog count or duration.

## 3. Recover without repeating uncertain effects

Honor scope changes and user-performed edits. Preserve reported changes as reported; do not repeat them or claim independent verification. Ask the service workflow to inspect current state before retrying an uncertain effect. Resume at the confirmed boundary without reopening settled decisions.

For a rejection, retain the exact action, target, stated reason, outcome, and completed independent work. Correct a demonstrable mismatch only within existing authority and the harness's retry rules; otherwise report the blocker. Distinguish denied, pending, and uncertain outcomes. This skill cannot control classifier decisions, waive mandatory dialogs, or turn silence into consent.

## 4. Retain proportionate state

Use existing task state rather than a mandatory new ledger. Retain authority by action/phase, current access limits, pending human decisions, user changes, and uncertain effects. Distinguish task-decision waiting, harness waiting, authentication, execution, and unknown state when observable. Tool wall time is not automatically processing time. Count distinct attended periods separately from dialogs and human button presses; report unknown measurements honestly.

## Composition

Load this skill when another workflow encounters an actual or expected intervention dependency. It updates authority/access/attention state in the existing plan; it does not change domain requirements or accept content. For teaching tasks, [teaching-materials](../teaching-materials/SKILL.md) owns semantic decisions and version status; for WebClass, [webclass-operations](../webclass-operations/SKILL.md) owns platform mapping, application, and readback. Use their operation plan rather than duplicate their policies. These are conditional composition links, not permission to install or activate skills.
