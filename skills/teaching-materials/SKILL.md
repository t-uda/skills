# Teaching Materials

Own educational meaning, scope, workload, evaluation criteria, and accepted content versions. Assessment, code, and generation checks apply only when relevant; a new lecture need not contain quizzes, code, or a historical baseline.

Resolve named companions from available skills or their source; sibling links locate them in this repository, not in every single-skill installation. If unavailable, report the capability gap and continue independent work; do not install or activate them implicitly.

## 1. Recover requirements and delivery constraints

Establish audience, learning goals, governing sources, conventions, accepted decisions, and allowed revision. Read actual relevant prior material when continuity matters; use agreed goals for new work. Preserve exclusions and later corrections. Compare prerequisites, reasoning, workload, and format where relevant; question count and answer-field count differ, and neither alone determines difficulty. Investigate vague requests for depth or variety before choosing how much to add. An explicit redesign brief permits redesign.

When WebClass delivery is requested, load [webclass-operations](../webclass-operations/SKILL.md) early for applicable objects, attributes, and technical constraints before finalizing content. For another destination, use its available delivery workflow. Separate technical limits, educational choices, and unresolved requirements.

## 2. Design content and applicable criteria together

Keep content and applicable attribute decisions in the existing canonical source/model with provenance and unresolved status. For assessments, define correct answers, scoring units/totals, accepted equivalences, and feedback intent from goals and governing policy. Honor explicit maxima and notation/numbering conventions; prior values and platform defaults are evidence, not policy.

Provide semantic criteria rather than assume a UI setting. This workflow updates educational requirements and version/decision status; the operator adds platform definitions, observations, mappings, and application checks to the same model. If a criterion cannot be represented, inspect the operator's concrete mismatch and supported alternatives, resolve only the affected semantic choice under existing authority, and update the version before regenerating its affected representations. Never silently weaken the criterion or let the operator choose new policy.

## 3. Validate meaning independently of delivery

Check source alignment, correctness, instructional consistency, and affected dependencies. For a new or substantially revised assessment, review the whole assessment and independently solve it from the student-visible prompts and supplied information before comparing against the proposed key. Use a separate solver/reviewer where available; otherwise perform a fresh derivation with the key withheld and disclose the limit of self-review. Agreement among generated solutions is not sufficient evidence.

Compare the independent result with the key, accepted alternatives, scoring, and feedback. Use counterexamples and boundary inputs to check ambiguity, missing assumptions, equivalence rules, partial-credit units, and totals. Confirm that a correct student response earns the intended credit and feedback, and that relevant wrong responses do not. Run code or domain-specific verification when applicable, using the stated environment and student inputs. Resolve contradictions in the source/model before delivery.

Scale verification to impact: a small wording or image edit needs affected-meaning and dependency checks, not an unrelated full assessment audit. Preserve accepted pedagogical choices outside the revision scope. Semantic validation is separate from saved UI readback, rendering, and platform grading-behavior checks owned by the delivery workflow.

## 4. Establish a reviewable version under actual authority

Present the relevant content, criteria, source correspondence, bounded differences, and validation together at the appropriate scale. Include solutions or complete code only when applicable. Distinguish a draft, a version the agent may finalize within existing delegation, and a version awaiting an explicitly reserved user decision. Record the basis of acceptance; never promote an agent draft to user approval or require owner approval for every revision. Content acceptance does not grant publication authority.

After acceptance, use that version as the baseline and expose bounded later changes. Load [human-intervention-management](../human-intervention-management/SKILL.md) when a reserved human review, tool permission, authentication, or interruption needs coordination; it manages attention and authority state, not educational correctness. Continue authorized independent preparation while a later decision is pending.

## 5. Maintain and deliver representations

Identify canonical-to-derived generation paths. Stage regeneration and compare affected content, attributes, and formatting before replacement so an old generator cannot erase accepted edits. Analyze shared defects without expanding edit authority; report stale representations rather than infer whole-set consistency from a partial check.

Provide the delivery workflow with the versioned content, applicable decisions and their authority, inherited scope, and unresolved issues in the existing model. Let it map controls and verify saved state, rendering, and safe behavior. Use [exposition-flow](../exposition-flow/SKILL.md) for explanatory order and [deslop-history](../deslop-history/SKILL.md) for unnecessary process residue when needed; use source/domain review skills when their checks are material. Keep platform operations, permission mechanics, course-specific values, and external-drive synchronization in their respective workflows/task state.
